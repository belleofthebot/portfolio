Analytics infrastructure and the executive dashboard

a commercial led lighting manufacturer · 2026 · small marketing team, no in house developer, no software spend

Built a company's entire web measurement capability from zero: governance, tracking architecture, and a dashboard leadership opens themselves.

the problem

The relaunch shipped five interactive tools that had never existed before, and there was no way to know whether anyone used them. A product configurator, a comparison tool, a lighting layout tool, a rebate finder, and a redesigned distributor portal. Some carry ongoing subscription costs. All were built on the assumption that customers wanted them. Nobody could prove it either way, because none of them emitted a single measurable signal.

Around that sat the wider gap: no way to see which product documents drive demand, no way to compare the new site against the old, no visibility into who was logging into the distributor portal. And a relaunch destroys the historical baseline unless the migration is planned deliberately. That window closes on launch day and does not reopen.

every event was tied to a live business question

The segmentation on that fifth row is the one worth pausing on. Login volume tells you the portal is busy. Login volume by user type tells you whether it is reaching distributors or just being used internally. Those are different businesses.

layer 0 · the audit, and what it found

  • The container was under the wrong account. The container provisioned for the new site sat under IT's account rather than Marketing's, meaning marketing would not own or be able to administer its own measurement infrastructure. I created a replacement under the correct account, coordinated with IT on access, briefed the agency to swap the installed snippet, and confirmed the old container was fully removed rather than left firing in parallel. That is access governance, not tagging, and it was caught before launch rather than during a crisis.
  • The legacy containers were empty. Both pre existing marketing containers held no tags, meaning the live site ran on hard coded on page tracking. That explained why nothing had ever been changeable without a developer, and justified building the new site differently.
  • Advertising tags were about to be orphaned. Ad platform and social insight tags on the legacy site had not been carried across to the new build. Flagged pre launch with a remediation path rather than discovered later as a silent gap in conversion data.

layer 1 · relaunch readiness

  • Three properties configured in parallel, covering the new site, the legacy site and the distributor portal, so post launch performance had a real baseline to compare against.
  • Tracking built and verified on staging before go live, not retrofitted. Configuration tags confirmed firing on every page via preview mode and hit level inspection, screenshotted for the record and confirmed back to the agency.
  • Measurement live on day one, including a cross property migration comparison, so the first question leadership asked after launch already had an answer waiting.

layer 2 · the tags, built by hand

No auto events, no plugins. Each system specified, built, tested in preview, verified in hit detail, published, and paired with a registered custom dimension so the data was reportable rather than merely collected.

  • File downloads. Document type resolved through a RegEx table variable mapping seven document categories, with product code extracted via custom JavaScript, so downloads report by what and by which product rather than as an undifferentiated total.
  • Product configurator. Event on the request button, with element variables reading the generated SKU and a validity attribute, capturing failed configurations too, because failure is a UX signal rather than noise.
  • Comparison tool. Element visibility trigger on the results container, with custom JavaScript extracting every compared product name plus a count, feeding the renewal case directly.
  • Interactive tools. Click tags scoped by destination URL, with one form tag deliberately scoped to the form's unique identifier rather than the page, preventing misfires on a form embedded in several locations.
  • Portal logins. Custom JavaScript variable reading user role from a page body class, firing a login event with a user type parameter, turning an untracked authenticated area into a segmentable audience with no backend work.

two judgment calls worth naming

  • The tracking I chose not to build. A third party rebate widget turned out to be a component library embed generating non deterministic element IDs on every render. DOM based tracking against it would have appeared to work and broken silently on the vendor's next release. I used the vendor's own reporting and shipped a page view metric as an honest interim measure. Declining to build fragile tracking is the harder call.
  • The discovery that avoided a backend project. Portal login tracking looked like API work with an external development partner. Inspecting the post login page showed the user role was already exposed in the markup, which collapsed a cross vendor project into a single variable.

layer 3 · the dashboard

A custom, access controlled web dashboard querying the analytics Data API directly. Eleven named report queries: totals, daily active users, top events, top pages, traffic sources by source and medium, file downloads by filename, product page performance, distributor portal logins by user type, portal logins daily, portal section usage, and form starts versus submissions. A twelfth cross property query produces the migration comparison, legacy platform against new, over a fixed since launch window. Date range selector and PDF export for circulation.

The engineering underneath is the part I would want asked about:

  • Service account authentication was hand rolled, not lifted from an SDK. Constructing and RSA signing a JWT assertion in code, exchanging it for an access token, and caching that token just under its expiry window. I read the authentication specification and implemented it.
  • Two tier caching: a token cache and a per date range payload cache, to stay well inside API quota.
  • Queries batched in groups of five per request rather than fired individually.
  • Least privilege by design. The service account holds read only viewer access and nothing else, documented at the top of the file.
  • Graceful degradation. Missing configuration returns a clear disabled state with the reason, rather than an error.

Why custom rather than off the shelf. Commercial reporting tools were evaluated and used first. They hit real limits: filters silently dropping between report views and needing reapplication, and interface changes that removed controls the team relied on. Building directly against the Data API gave complete control over what was measured, how it was filtered and how it was presented, at no recurring cost.

outcome

Every event was specified against a business question rather than collected by default. The five interactive tools introduced in the relaunch went from producing no measurable signal at all to being individually reportable, including subscription carrying tools whose renewal case now rests on usage data rather than assumption.

  • Measurement verified on staging and live on day one of the relaunch, with a cross property migration comparison available from launch.
  • Six custom event families feeding a new property, plus two further properties configured to preserve the pre relaunch baseline.
  • In daily use by the marketing team at zero recurring tooling cost, replacing recurring hours of manual reporting each week.
  • Measurement infrastructure now owned and administered by Marketing rather than borrowed from IT.

honest limitation

A majority of early portal login events recorded a blank user type. I found it, documented it as a post launch refinement item and flagged it to stakeholders rather than presenting the data as clean. Until it is fixed that segment is directional rather than authoritative, and I would rather say so than have someone build a decision on it.
